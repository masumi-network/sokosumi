## Summary

Only the **orchestrator** assigned to a task can attach jobs to it. Tasks expose a list of linked job IDs; the API supports adding a single job per request (orchestrator only) and listing all jobs for a task (user or orchestrator with access). Jobs cannot be removed from a task (add-only).

## Key changes

- **Schema (database)**
  - `Job`: optional `taskId` (FK to Task, `onDelete: SetNull`) and index.
  - `Task`: `jobs Job[]` relation.
  - Migration: `20260202120000_add_job_task_relation`.

- **Core API**
  - **POST /v1/tasks/:id/jobs** – Add one job to a task. **Orchestrator only** (assigned to the task via `requireOrchestratorTaskAccess`). Body: `{ jobId: string }`. Job must exist and `job.userId === task.userId`. Response: 201 with full job (jobSchema).
  - **GET /v1/tasks/:id/jobs** – List jobs for a task. Access: user (task owner) or orchestrator with task access (`requireTaskAccess`). Response: 200 with array of jobs (jobsSchema).
  - **GET /v1/tasks/:id** and **GET /v1/tasks** – Task payloads now include required **jobIds** (string[]), always present (empty array when none). Task fetch uses `taskInclude` with `jobs: { select: { id: true } }`; `mapTask` adds `jobIds: task.jobs.map(j => j.id)`.

- **Schemas**
  - `addTaskJobRequestSchema` for POST /tasks/:id/jobs.
  - `taskSchema`: new required field `jobIds: z.array(z.string())`.

- **Types / helpers**
  - `taskInclude`: added `jobs: { select: { id: true } }`.
  - `mapTask`: added `jobIds` from `task.jobs`.

## Architecture

- Job–task link is add-only (no endpoint sets `taskId` to null).
- **Adding jobs**: only the orchestrator assigned to the task (`task.orchestratorId === authContext.orchestratorId`) can call POST /tasks/:id/jobs. Users receive 403.
- **Listing jobs / task with jobIds**: user (task owner) or orchestrator with task access via `requireTaskAccess`.
- Job must belong to task owner (`job.userId === task.userId`). Job responses reuse existing job include/flatten (jobWithEvents, jobWithTransaction, jobWithPurchase, flattenJob).
