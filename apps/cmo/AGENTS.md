# CMO app

CMO is the product at cmo.xyz (see **CMO** and **Sign in with Sokosumi** in [GLOSSARY.md](../../GLOSSARY.md), and [ADR 0045](../../docs/adr/0045-cmo-signs-in-through-core-oauth-provider.md)). This app is its own Next.js deployment at app.cmo.xyz, not part of Web.

- **Own components.** Build every component inside `apps/cmo`; Web's components stay Web's.
- **Submit buttons.** Use `SubmitButton`; it shows the loading bar and keeps the pressed button focused.
- **Brand and design system.** Read [`DESIGN.md`](DESIGN.md) before copy work (product, voice, agent naming) and [`design-system.md`](design-system.md) before UI work (corporate neobrutalism: the five rules, colour and type tokens, components, how Cuso is used). Both are CMO's own, separate from Web's, and the CMO.XYZ-Style-Guide repository syncs from them. Take every colour, size, radius and shadow from the tokens in the `:root` block of `src/app/globals.css`; `/design-system` (local and preview deploys only) renders them with the base classes, Cuso's poses and the onboarding parts in both themes, and `/design-system/onboarding/{signed-out,name,hire,research,research-question,research-slow,research-error,research-words,brand,brand-fix,plan,briefing-plan,briefing-week,briefing-checks,briefing-ads,briefing-change,approve,connect,connected,month,away}` (one per state on the Brief me boards) and `/design-system/app/{chat,strategy,calendar,results,brain,channels,settings}` (`?theme=dark`) render each real screen over fixture data. `src/components/showcases.css` draws the networks' own UIs (the month's account previews), so the visual guards skip it. `src/design-guards.test.ts` holds the locked rules: one hard shadow and no blur, radii from tokens, type only in the scale's sizes, Iris, green and yellow as fills only, no gradients, colour literals only in the `:root` block of `globals.css`, the face only through `--font-sans`, no em dashes, hedges or hardcoded agent name in copy, an `alt` on every image, and no removed focus outline.
- **Mascot.** The mascot is called Cuso. `public/mascot.glb` and `public/mascot.webp` come from the style guide's `3D Mascot` folder, shrunk with `npx @gltf-transform/cli optimize --compress quantize --texture-compress webp --texture-size 2048 --simplify false` and an 800px WebP. `src/components/mascot.tsx` renders it with three.js over the still image. The header logo is the CMO.XYZ wordmark from the concept canvas, inlined in `src/components/logo.tsx` in `currentColor`. The pointer mark (`public/logo.svg`) and the app icons (`public/icon.svg`, `favicon.ico`, `apple-icon.png`, linked from `metadata.icons` in `src/app/layout.tsx`) redraw the mascot's pointer with eyes as flat vector art. They live in `public/` so their URLs stay stable for outside links. `icon.svg` has a transparent background and a black outline so it reads on light and dark browser tabs; `favicon.ico` (16, 32, 48 px) is rasterised from it, so change the SVG first. `apple-icon.png` keeps a solid black tile because iOS fills transparency with black.
- **Landing page.** A signed-out visit to `/` shows the marketing site in `public/site/`, served as is by `src/proxy.ts`. It came from the archived `masumi-network/cmo-website` repo; the only change is the `/site/` prefix on its paths. Its waitlist posts to `src/app/api/waitlist` (needs `SOKOSUMI_API_KEY`). Create account starts with the website: the unlinked `/start` asks for it signed out, keeps it in the `cmo-website` cookie (a day) and goes on to Sokosumi's Register with it (and a Create account link's other parameters) as the sign-up context. Back from sign in, Home starts reading the kept website on its own; the first start, or Start over, forgets it. A failed sign in costs nothing: `/login` says the website is kept, and Try again creates the account again. `/signup` without a website goes to `/start` with its parameters; `/signup?url=` goes straight to Register, and since a link is a cross-site GET its website only fills the hiring form on return. `/signin` still goes straight to Sokosumi's Log in. Web gives those pages CMO.xyz's look when CMO's callback is the redirect. Sign-in errors land on `/login`, which redirects to `/signin` when there is no error.
- **Brand Brain media and questions.** Hiring screenshots the homepage on a desktop and a phone right away (`captureCmoHomepage`), so the Brand Brain opens with it. Once Cuso saves the Brand Brain essentials, Core screenshots the brand's key pages (and its homepage on a phone) and each competitor's homepage with headless Chromium, keeps the large pictures from the brand's pages, and saves each file as soon as it is taken as the Project's files (organization Files, confirmed on Cuso's Project) under "Brand research" (`apps/core/src/services/cmo-brand-media.service.ts`). The file names carry what CMO shows: page labels, competitor names and each picture's alt text. The brand's look (logo, colours, fonts) is the Project's logo and DESIGN.md, which hiring fills from the site (`cmo-brand-visual.service.ts`). Locally set `CHROMIUM_EXECUTABLE_PATH` in `apps/core/.env` to your Chrome. What research could not settle becomes yes/no `questions` on the Brand Brain, asked one at a time in the chat while Cuso finishes reading ("Later" skips them, kept in CMO's cookie as `questions`); a yes lands in its section as a confirmed finding. A no lands as what is true instead ("Not true: …" without a note) and its question stays `corrected: false` until that section's answer is rewritten; the next strategy request tells Cuso to rewrite those sections with `save_brand_brain` before he plans (`brandBrainCorrections`). Core starts the first plan itself when the research turn ends with the essentials saved (`startCmoPlanAfterResearch`, from the turn's settlement: Core runs one turn per bot at a time), so the founder reads the Brand Brain while Cuso writes. "Looks like us" in the brand check approves the Brand Brain; asking for a plan while one is written returns that turn, a change request or patch is refused until it lands (the screen holds it), and Try again's `restart` replaces a plan past twice the usual time. The plan saves in two parts: the plan part first (the screen shows it at once), then the calendar (week one in full, weeks two to four as titles). A save that breaks a hard rule (a summary of at most 20 words, at least 16 pieces, approach and pillar shares within 7 points) is refused at save time and names the rule (`cmoPlanRuleProblems`), so the post-save review never sends Cuso back for them. A brand fix (`POST /v1/cmo/projects/{projectId}/brand/fix`, `fixCmoBrandSection`) is stored on its section as `fix` at once, or, without a section (the brand check's Fix something, a reply in words), on the Brand Brain's own `fix` as a general correction that Cuso applies to every section it changes; the page shows either as being fixed until its `fixed` turns true; a short turn (`cmo:strategy:<bot>:fix:<time>:<newest fix sent>`) rewrites only that section, and patches the plan when one exists; the section's `fix.fixed` turns true when its answer changes ("Fixed by you"). While Cuso is busy the fix waits, and starts when any of his foreground turns settles (`afterCmoTurn` → `startNextCmoChange`); a fix turn that ended never retries the fixes it was given. A no on the plan, a pace and an ad budget are patches (`requestCmoStrategy({ patch: true })`, `cmo:strategy:<bot>:patch:<time>`): `save_strategy` part patch changes only the entries and fields it sends, and the plan's `patched` keeps each changed entry as it was until the next whole save. The overview's `work.change` says `fix`, `patch` or null for a whole plan. Hiring also starts a quick look (`cmo-quick-look.service.ts`): one structured call on the homepage, stored as the Brand Brain's `preview` until the essentials replace it, never read by a turn. The overview's `research.groups` are six groups of sections, derived from what is saved.
- **After approval: the month is made at once.** Hiring is **Brief me** (the three Brief me boards on the concept canvas): the page shows one result at a time with See more for the full detail (the research steps, the Brand Brain, the whole strategy, the calendar, the market map), and a bar at the bottom shows Cuso, the seven stages (Website, Research, Brand check, Plan, Briefing, Go live, Your month) and either what he is doing or the one thing he needs. `components/onboarding/brief.ts` derives everything from the overview: the stage, the timeline (the plan writing behind the brand check is dashed), the chat's queue with its count (`briefAsks`), the working line in Core's own counts (groups, sections, pieces; never a time) and what Cuso does meanwhile. Working, the bar is a polite live region and says nothing needs you; needing you, the chat opens on one question with real buttons and a free-text field, moves focus to it, and Later or Esc folds it (Later skips the brand questions and the plan's checks on this device). The page never asks. The stages are buttons once finished (the current one too; the ones ahead are disabled): a finished one shows its page read-only (`StageReview` in `brief-main.tsx`: the site, the research, the Brand Brain, the plan, the answers, what was approved and connected) under a "Back to <current stage>" line, while the chat stays on the current question; the viewed stage is underlined in ink, apart from the progress fill. It is local state with no URL, and it stays put when the current stage moves on. On a phone the step line and strip are one button that opens a sheet of the stages. Past the usual time the line says so; past twice it the chat offers Try again. The briefing has four steps, one question each: the plan (goal and three moves; Sounds right, or a change in words), week one and pace (Keep, Fewer, More, or a note), the plan's checks (all the nos become one patch once the last is answered), and ads only when the plan has ad pieces (Yes, Change amount, No ads). Every change is a patch (`requestCmoStrategy({ patch: true })`); the next question waits until it lands. Core keeps no record of Sounds right, Keep or Yes to the budget, so they are kept per device (`cmo-briefed-<project>` in localStorage), as is the stage this device last showed (`cmo-seen-<project>`), which decides the welcome back ("5 quick things need you"). Once the briefing's last step is done the stage is Go live: approval (the one gate, owner or admin, with the month in one table) comes first, then Go live waits for one of the social networks the plan posts to, each connected in a popup; the rest stay drafts, and ads connect in Settings. Launch only enables once a network is connected, and Core ends hiring on the first connection, so Launch and Your month (the first post, pieces written of the month) are client-side; Go to Today runs `finishAccounts` (cookie and redirect), because a cookie set in a server action re-renders the page into the app. There is no billing step yet (`isCmoSubscribed` in `cmo-billing.service.ts` lets every Cuso run on his organization's credits until CMO's own checkout exists). Every hire gives its organization 10,000 free credits, once per Project (`grantCmoStarterCredits`), wherever it lands (ADR 0065). Once the plan is approved, Core starts one background run that writes every piece and, for a format with a picture or video, its `visual` (what it shows) and `visualFileIds` (the brand pictures it is made from) (`apps/core/src/services/cmo-production.service.ts`). Its brief holds the Brand Brain's named customers, results and reviews (`cmoProofPoints`), which Cuso's context otherwise sums up. Core makes the media, not Cuso: `cmo-media-maker.service.ts` starts each piece's picture once (a job key names its version, piece, slot and visual, so racing callers start one job and a new visual starts over), at most three at a time per the studio's limit, from the visual and the brand pictures, makes a video by animating a still made from them, puts the file on its post (or a file piece's `mediaFileIds`) and schedules a post with media on a connected network. A settled job moves the month on at once (`nudgeCmoMonth`); a slot that fails twice goes back to Cuso for a new visual. Cuso's own runs may not call `generate_image` or `generate_video`; the owner still can in chat. A pending piece whose words are written and whose media Core is making needs no run, and a `wait_for` follow-up counts as a working run. A Soko Bot's post in a month is refused when it says what another post of the month says, or carries a picture already on another post. Repeats are judged by meaning (`findRepeats` in `apps/core/src/lib/repeats.ts`: embeddings, cosine at or above `REPEAT_CUTOFF`, calibrated with `scripts/calibrate-repeats.mts`); a post's text is checked before its save's transaction (`ownMessageProblem`), and when the embedding model fails the check is skipped. The plan review names, in one review, each group of calendar titles that say one thing and each story told in more than two pieces (`cmoCalendarRepeats`), and the made month's drafts the same way; it answers four plan saves and two calendar saves a turn, since each fix resends the whole calendar. The plan review allows at most four videos a month. Core decides when a piece is ready and starts another run for anything missing, at most four a day (`/sync/cmo-production`, every ten minutes; locally call it yourself). The calendar must hold the plan's mix and its content pillars, each pillar with a share, every entry naming one (the plan review checks both), so making it in one go keeps the ratios. Every production run's brief carries the writing skills for its networks in full (`writingSkillsBrief` in `@sokosumi/soko-bot`: brand voice, post formatting, hooks and endings, one skill per network, ads, newsletter and SEO); every turn's context lists them (`writingSkills`), and Cuso opens one with `read_writing_skill` before he writes a piece in chat; admins read them at `/admin/writing-skills` in Sokosumi. Once the month is made, the month review (`cmo-month-review.service.ts`, stored in `marketing_strategy.monthReview`) reads every piece: Jev says which pillar it is about, whether it follows each judged rule of its skill (one question per rule, only the rules for its format) and whether it sounds like the Brand Brain's voice; rules that count characters or items are checked in code (`cmoCountedProblems` for files, the save check for Social posts), because Jev cannot count. Each read is charged to the bot's payer at its metered cost (`recordSokoBotCheckUsage`, once per version and round). One rewrite run gets the pieces still to come that miss a rule, the voice, or (when a pillar's made share is more than seven points off its plan) their pillar, each with the exact reason; Jev reads the month again after it, and nothing is rewritten twice. Strategy shows each pillar's made share beside its planned one, and the Calendar filters by pillar. Social pieces are the approved version's Social posts; every other piece (an article, a page fix, ad copy, a newsletter issue) is saved with `save_strategy` part pieces and written by Core as a Markdown file in the Project's Files (`marketing-strategy-files.service.ts`), which CMO's piece sheet opens through `/v1/cmo/projects/{projectId}/calendar/{id}/text`. The app's Calendar page (`/calendar`) shows every piece as a card by week, filtered by network or pillar; its sheet steps to the next piece (arrows). Strategy holds the plan only and links there. Pictures are JPEGs (Instagram takes nothing else), made from the brand's own pictures (`brandPictures` in Cuso's context: the page screenshots first, then the photos from its pages, all saved as JPEG by the brand capture). Carousel formats list their slide counts in `CMO_CHANNELS`; Core makes each slide from the one visual, and Instagram publishes two or more images as one carousel. The daily run then fills gaps, answers comments and checks the news last. Reading the web blocks post changes for the rest of a run, so news changes only the calendar, and the next production run makes the piece. The chat opens on one welcome once hired: the overview's `hiredAt` (the first approval, read from the first production run's id because a later approval clears the earlier one) hides the hiring messages and cards, which the owner already went through. Making the month shows in the chat as one progress card (`overview.production`, linking to the Calendar); every report a production run files is stored as kind `production` (`reportCmoUpdate`, whatever kind Cuso gave it), left out of CMO's chat and shown in Sokosumi's chat as its headline alone.
- **Strategy and measurement.** The strategy is one sentence (who, positioned as, how they find you, the offer) built on a funnel; each stage says who runs it (Cuso, the owner, or both) and whether its number is measured or estimated. Every first plan starts at the All-in pace and Cuso suggests an ad budget; the owner can change either. A pace, a budget, a no or a change in words patches the plan in place: a patched entry shows its old words struck through and its new ones typing in, and nothing else moves. On Go live, Connect opens the network's sign-in in a popup that ends on `/connect/done`, which tells that Project's onboarding on CMO's own origin (`postMessage` to the opener, or a same-origin `BroadcastChannel` when the provider cut the opener) and closes; the flow polls at once (`lib/connect-window.ts`). A blocked popup falls back to the redirect. A tile's fix goes to its section (`fixBrandSection`) and the tile says "Fixed by you" once Cuso has rewritten it. Channels connects Google Ads or Meta Ads to Cuso's Project (`/v1/cmo/projects/{projectId}/ads/*` in `cmo-ads.service.ts`, back through `/ads/callback`, `/ads/choose` when the login reaches several accounts). Cuso writes a google_ads search piece with `searchAd` (kept on its `marketing_strategy_file` row); an owner or admin presses Launch, and Core builds the Google campaign from it and starts it. Core refuses any start that takes running campaigns past the approved plan's ad budget a day (monthly / 30) or uses an account in another currency. Cuso never starts an ad himself; Meta campaigns are not created from CMO yet. A launched search ad targets people in its `location` (Google's presence setting; an ad without one is refused), caps a click at Cuso's `maxCpc` and never above a third of its daily budget (`cmoMaxCpc`), and excludes `CMO_NEGATIVE_KEYWORDS` (jobs, pirated copies) plus Cuso's `negativeKeywords`. Links in Cuso's posts to the owner's site get UTM tags (`tagOwnLinks`: the network, `social`, `cmo-YYYY-MM`). Weekly reviews end with a verdict (hold, fix, test, investigate) and learnings on their report; the next turns read the last four as `weeklyLearnings`. The owner connects Google Analytics, Search Console and, for a Shopify shop (the Project's `sitePlatform`, read once from the homepage), Shopify on the strategy's "How we know it works" tab (the briefing's See more, and the Strategy page). These connect to Cuso's own Soko Bot through the generic Composio integration path (`/v1/cmo/projects/{projectId}/measurement/{provider}/connect` and `/finalize`, back through `/measure/callback`), and Cuso reads them with `run_integration_tool`.
- **Server-side Sokosumi.** CMO holds no database. Its server reaches Sokosumi through Core's OAuth provider and `/v1`. Hiring Cuso asks where he goes: a new organization named after the website (the default), or any organization the person belongs to ("Where" on the hire form, shown only to a person with organizations; never the personal workspace). Every hire creates a new Project, and an organization may hold several Cusos, one per Project ([ADR 0065](../../docs/adr/0065-a-cuso-hire-goes-into-a-new-or-an-existing-organization.md)). Any member may hire; a hire into an existing organization leaves its name, plan and the person's preferred organization alone, and Core checks the hirer's Seat and balance before creating a Project, counting the starter credits that a successfully provisioned Cuso brings, so an empty organization can hire on them. CMO is invite-only for now: only a person whose Sokosumi email, or its `@domain`, is on Core's `CMO_HIRE_ALLOWLIST` may hire, and Core refuses anyone else before creating anything (`cmo_hire_not_allowed`), because every hire grants credits. `GET /v1/cmo/cusos` answers `mayHire` beside the Cusos; without it the picker leaves out "Hire a new Cuso", and the hire form (no Cuso, or `?hire=1`) becomes the invite-only page (`SignedIn` with `inviteOnly`). Everything else stays open to whoever works with a Cuso. Core declares each refusal with a `kind` (`cmo_hire_not_allowed`, `organization_seat_required`, `insufficient_balance`, `organization_limit_reached`, `organization_membership_required`), and the hire form names its reason. Cuso is that Project's shared Soko Bot: every member of the organization works with him in his shared room, and only its owners and admins approve the strategy ([ADR 0061](../../docs/adr/0061-cuso-is-a-shared-project-bot.md)). Core keeps no CMO record: Cuso is found as a Project's shared bot on CMO's version, one per Project ([ADR 0062](../../docs/adr/0062-cmo-keeps-no-data-of-its-own.md)), and `GET /v1/cmo/cusos` lists every live Cuso the person can use, newest first. The home page (`home.tsx`) opens the Cuso the address names (`project`), else the one last opened on this device (the `cmo-last-cuso` cookie, written by `proxy.ts` for an address naming an accessible Cuso and by the hire action), else the only one, else the **Cuso picker**, else the hire form; an address naming a Project the person can't use opens the picker or hire form. `?cusos=1` ("Your Cusos" in the account menu on the hire form once the person has a Cuso, while hiring and in the sidebar) opens the picker, `?hire=1` the hire form. Sokosumi's preferred organization plays no part. From there every Cuso action names that Cuso's Project (`home.tsx` binds the rendered overview's `projectId` to each action; they call the `/v1/cmo/projects/{projectId}/…` routes), and provider callbacks (ads, measurement, social connections) carry it as `project` in their return address, so a workspace switch in Sokosumi never moves a flow to another Cuso. Start over (Settings, or the account menu while hiring; `POST /v1/cmo/projects/{projectId}/start-over`) archives that Cuso and cancels his unsent posts, then opens the hire form with a new organization selected, even when other Cusos remain (a person who may not hire gets the picker, which is the invite-only page when none remain); his organization and Files stay, and his room is renamed after his website ("Cuso · acme.io"). Hiring into a new organization again before any plan of his was approved stays in that organization, renamed after the new website, so the earlier chat sits beside the new Cuso's (`organizationLeftWhileHiring`); a retry after a failed hire reuses its empty organization. An existing organization is never reused or renamed. The name comes from the account: only a person with neither a valid first and last name nor a display name gives one first.
- **Evals.** A change to how Cuso behaves (his skills, prompts, tools, version or model, or Core's checks on his plan and posts) runs the CMO evals before it merges, and new Cuso behaviour ships on a new Cuso version. See [evals](../../docs/agents/evals.md).

## Cuso's animations

Each still in `public/cuso/` has an MP4 beside it, made once by `scripts/animate-cuso.ts` and committed; nothing is generated at runtime. The script sends each still to Seedance 2.5 (`bytedance/seedance-2.5` on the AI Gateway) as first and last frame, so a clip starts and ends on its still, then encodes it with ffmpeg (H.264, `yuv420p`, `+faststart`, no audio, about twice the size it is shown at). The prompt for each still lives in the script. Run it from `apps/cmo` with ffmpeg installed and a Core `.env` that holds `AI_GATEWAY_API_KEY`:

```sh
node --env-file=../core/.env scripts/animate-cuso.ts            # every clip
node --env-file=../core/.env scripts/animate-cuso.ts hero done  # some clips
node scripts/animate-cuso.ts --reencode                         # re-encode the last raw clips, no Seedance
```

`CusoClip` (`src/components/cuso-clip.tsx`) plays a clip with its still as the poster and shows only the still under `prefers-reduced-motion` (and on the server); a clip first plays once half of it is on screen, so the hire hero below the fold on a phone waits to be seen. `CusoAvatar` plays its pose once, then again every 30 seconds; past chat messages keep the still. The bar's Cuso plays his pose for the state (reading, thinking, needs you, done); the hero, the reading scene and the celebration only show on the `/design-system` page now. Keep the stills: they are the posters and the reduced-motion fallback.

## Run CMO locally against a local Core

Cuso needs Core's CMO routes and migration, so a branch that changes them runs against its own Core and database, never the shared dev Neon branch.

1. **Database.** Create an empty local Postgres database and point `apps/core/.env` and `packages/database/.env` at it. On Postgres 14/15, `prisma migrate deploy` fails on an old migration; create the schema from the Prisma files instead: `CREATE EXTENSION pg_trgm;`, then apply `pnpm exec prisma migrate diff --from-empty --to-schema prisma --script` (from `packages/database`) with `psql`. Seed test accounts with `CLOUD_AGENT_DB_FORCE=1 node scripts/agent-db/seed-auth-fixtures.mjs` (`alice@sokosumi.test` and the others, password `Password123!`).
2. **Core and Web.** Core's `.env` needs `SOKO_BOT_ENABLED="true"`, `SOKO_BOT_RUNTIME_ADAPTER="in-process"` and an `AI_GATEWAY_API_KEY`, with `BETTER_AUTH_URL` and `WEB_APP_BASE_URL` on your local ports. Web needs Node 26 (`.nvmrc`, `apps/web` `engines`) and `CORE_APP_BASE_URL` / `NEXT_PUBLIC_CORE_APP_BASE_URL` on that Core.
3. **CMO's OAuth client.** Signed in as a test account, `POST {core}/auth/oauth2/create-client` with `token_endpoint_auth_method: "client_secret_basic"`, `grant_types: ["authorization_code", "refresh_token"]` and `scope: "openid sokosumi:api offline_access"`. Better Auth only registers `https` redirect URIs on non-loopback hosts for web clients, so register a placeholder, then set the real callback on the row in your local database: `UPDATE "oauthClient" SET "skipConsent" = true, "redirectUris" = ARRAY['http://localhost:<cmo port>/api/auth/callback/sokosumi'] WHERE "clientId" = '<client_id>';` (authorize matches the URI exactly). Set Core's `CMO_OAUTH_CLIENT_ID` to this `client_id` and restart Core: every `/v1/cmo/**` write from another client, an API key or a session gets 403 `cmo_client_required`, and none is allowed while it is unset.
4. **CMO.** `apps/cmo/.env.local` holds `BETTER_AUTH_URL` (CMO's origin), a random `BETTER_AUTH_SECRET`, `CORE_APP_BASE_URL`, and the client's `SOKOSUMI_OAUTH_CLIENT_ID` / `SOKOSUMI_OAUTH_CLIENT_SECRET`. Start it with `PORT=<cmo port> pnpm dev`.

The in-process runtime has no sandbox, but it runs Cuso's read-only web tools (`web_search` through the AI Gateway, `web_fetch`) itself, so Cuso reads the real site locally too. Shell and workspace tools stay sandbox only.

To run a CMO rhythm now instead of waiting for its schedule, move its `nextRunAt` into the past (`soko_bot_schedule.systemKey` is `cmo-daily-run` or `cmo-weekly-review`; the column is UTC) and call `GET {core}/sync/soko-bot-schedules` with `Authorization: Bearer <CRON_SECRET>`.
