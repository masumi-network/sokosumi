# CMO app

CMO is the product at cmo.xyz (see **CMO** and **Sign in with Sokosumi** in [GLOSSARY.md](../../GLOSSARY.md), and [ADR 0045](../../docs/adr/0045-cmo-signs-in-through-core-oauth-provider.md)). This app is its own Next.js deployment at app.cmo.xyz, not part of Web.

- **Company.** CMO.XYZ belongs to Sumico, Inc., not utxo AG. Name Sumico, Inc. wherever the product names its company. "utxo AG" in eval cases, fixtures and Core is a customer and a workspace, not the owner; leave it.
- **Own components.** Build every component inside `apps/cmo`; Web's components stay Web's.
- **Nothing opens or names Sokosumi.** The owner works with Cuso in CMO, so a reply, receipt, card or link never leads into Sokosumi or names its features (Content Studio, Tasks, Files). Core strips links into Sokosumi from a Cuso reply (`withoutSokosumiLinks` in `@sokosumi/utils`, applied in `buildActionResponse`), and the chat applies it again when it renders (`renderInline`), which also covers older messages. What Cuso did on a request shows as his own message (`RequestNote`), flat and in his words. Guards: `action-response-cmo.test.ts` in Core runs every receipt on a Cuso turn, "renderInline" in `cmo.test.tsx`, and the persona test in `packages/soko-bot/src/__tests__/cmo.test.ts`. Sign in with Sokosumi is the one place the name belongs.
- **Submit buttons.** Use `SubmitButton`; it shows the loading bar and keeps the pressed button focused.
- **Brand and design system.** Read [`DESIGN.md`](DESIGN.md) before copy work (product, voice, agent naming) and [`design-system.md`](design-system.md) before UI work (neobrutalism, the landing page's look: the five rules, colour, line, shadow and type tokens, components, how Cuso is used). Both are CMO's own, separate from Web's, and the CMO.XYZ-Style-Guide repository syncs from them. Take every colour, size, line width, radius and shadow from the tokens in the `:root` block of `src/app/globals.css`; `/design-system` (local and preview deploys only) renders them with the base classes, Cuso's poses and the onboarding parts in both themes, and `/design-system/onboarding/{hire,reading,writing,asking,brand,plan,planning,launch,launch-connected,subscribe,subscribe-confirming}` and `/design-system/app/{chat,strategy,calendar,seo,results,brain,channels,settings}` (`?theme=dark`) render each real screen over fixture data. `src/components/phone-feeds.css` and `showcases.css` draw the networks' own UIs, so the visual guards skip them. `src/design-guards.test.ts` holds the locked rules: the token values the docs name, borders only as the 1px hairline or a line-width token, shadows only from the two hard shadow tokens (4px and 6px, and their Iris and strip colours) and no blur, a hard shadow only on something to act on (a button, link, input or picked tile; never a card that is not a button), radii from tokens, type only in the scale's sizes, Iris, green and yellow as fills only, no gradients, colour literals only in the `:root` block of `globals.css`, the face only through `--font-sans`, no em dashes or hedges in copy, an `alt` on every image, and no removed focus outline.
- **Mascot.** The mascot is called Cuso; his drawings live in `public/cuso/` (see Cuso's poses below). The logo (`src/components/logo.tsx`) is the approved stacked-text lockup from the [Masumi Family Brand Guide](https://github.com/masumi-network/Masumi-Family-Brand-Guide) (`logos/cmo-xyz/lockups`), copied unchanged into `public/logo/`: the black file on a light page, the white one on a dark page, never recoloured and never narrower than 120px. The app icons (`public/icon.svg`, `favicon.ico`, `apple-icon.png`, linked from `metadata.icons` in `src/app/layout.tsx`) are the guide's Iris monogram, approved on white and on black. They live in `public/` so their URLs stay stable for outside links. `favicon.ico` (16, 32, 48 px) is rasterised from `icon.svg`, so change the SVG first. `apple-icon.png` keeps a solid black tile because iOS fills transparency with black. `public/site/assets` holds the same three icons for the marketing site.
- **Landing page.** A signed-out visit to `/` shows the marketing site in `public/site/`, served as is by `src/proxy.ts`. It came from the archived `masumi-network/cmo-website` repo; the only change is the `/site/` prefix on its paths. Its waitlist posts to `src/app/api/waitlist` (needs `SOKOSUMI_API_KEY`). Create account and sign in are the unlinked `/signup` and `/signin`, which go straight to Sokosumi's Register and Log in; Web gives those pages CMO.xyz's look when CMO's callback is the redirect. Sign-in errors land on `/login`, which redirects to `/signin` when there is no error. Those Web pages name CMO.XYZ, not Sokosumi, in the tab title, the cookie notice and the imprint link, and Core's sign-in code email does the same for a code asked for inside CMO's OAuth request (`signsInToCmo`); the terms and privacy links are still Sokosumi's, because CMO.XYZ has none. Sign out leaves the `cmo-signed-out` cookie (`src/lib/signed-out.ts`): the Sokosumi session outlives CMO's, so the next sign-in sends `prompt=login` and Sokosumi shows its form, where the person can use another email; the proxy drops the cookie once someone is signed in.
- **Brand Brain media and questions.** Hiring screenshots the homepage on a desktop and a phone right away (`captureCmoHomepage`), so the Brand Brain opens with it. Once Cuso saves the Brand Brain essentials, Core screenshots the brand's key pages (and its homepage on a phone) and each competitor's homepage with headless Chromium, keeps the large pictures from the brand's pages, and saves each file as soon as it is taken as the Project's files (organization Files, confirmed on Cuso's Project) under "Brand research" (`apps/core/src/services/cmo-brand-media.service.ts`). The file names carry what CMO shows: page labels, competitor names and each picture's alt text. The brand's look (logo, colours, fonts) is the Project's logo and DESIGN.md, which hiring fills from the site (`cmo-brand-visual.service.ts`). Locally set `CHROMIUM_EXECUTABLE_PATH` in `apps/core/.env` to your Chrome. What research could not settle becomes yes/no `questions` on the Brand Brain, asked one at a time on the Research step while Cuso reads; a tap answers at once and moves on, and "Add more details" sends the owner's words with the next tap, whatever the answer ("Skip for now" keeps them in CMO's cookie as `questions`, and the Brand step lists what is left); a yes lands in its section as a confirmed finding (with the details), and a not sure lands only its details. A no lands as what is true instead ("Not true: …" without a note) and its question stays `corrected: false` until that section's answer is rewritten; the next strategy request tells Cuso to rewrite those sections with `save_brand_brain` before he plans (`brandBrainCorrections`). Core also keeps the no as a fix on its section (`answerCmoBrandQuestion`): once Cuso's current turn ends, a short fix turn rewrites that section and patches the plan, if there is one (`startNextCmoChange`). Cuso starts the first plan himself once the research turn ends (`startCmoPlanAfterResearch`), so the founder reads the Brand Brain while he writes. The Brand step shows the business's logo on the promise card, a "Your look" row with the DESIGN.md colours, fonts and file (`brandVisual`), and Cuso's market map (`reveal.map`) above the competitors. "Looks like us" approves the Brand Brain and asks for a plan only when none exists yet; Core hands back a plan already being written, and the Plan step shows its progress. An edit or a typed correction on the Brand step is a fix on its section too (`POST /v1/cmo/projects/{projectId}/brand/fix`).
- **Words.** People and Cuso call his month of marketing the strategy, never the plan; a plan is a paid CMO plan (a tier). What he makes is a post (or an ad, an article, an email) to people, and a piece only in code and these notes. The agent is always Cuso; nobody names him. Code, ids and these notes still say plan for the strategy (the `plan` step, `plan-step.tsx`, `save_strategy` part `plan`).
- **After approval: the month is made at once.** Hiring has five steps: Research, Brand, Strategy, Subscribe and Launch (`components/onboarding/step.ts` decides which from the data). The plan's yes/no questions sit on the Plan step as assumption chips; a no sends the plan back to Cuso (Update strategy). Approving the plan opens Subscribe, the CMO plan checkout ([ADR 0068](../../docs/adr/0068-cmo-sells-its-plans-through-polar.md)): Core's step is `checkout` from approval until the Project has a CMO subscription that has not ended (or Tester credits), then `accounts` until a network is connected, then `done`. Subscribe leads with what the approved month holds (pieces, channels, pictures and videos), offers the plans (`GET /v1/cmo/plans`, read from Polar's products, loaded with the page while the strategy waits for approval too), monthly or yearly with the yearly saving, with the plan that fits the plan's pace picked and marked, then Polar's hosted checkout (`POST /v1/cmo/projects/{projectId}/checkout`; any member may pay). Polar sends the person back to `/?project=…&step=subscribed`, which shows the confirming state and polls the overview until Core's step leaves `checkout`: on to Launch, or the app when an account was already connected; a person who left without paying lands on the plans again. Launch waits for one of the social networks the plan posts to (each row shows its pieces), and ads (always optional, they cost the owner money) and the channels Cuso proposes can be added there or later; the newsletter list is not set up while hiring. Launch only enables once a network is connected, and pressing it shows the celebration (no server call); Go to Today runs `finishAccounts` (cookie and redirect) and opens the app. A Cuso with Tester credits (`billing.hasTesterCredits`: a tester skipped the subscription, or he was hired before CMO plans) owes no checkout and goes from the plan straight to Launch. The work is gated by `isCmoSubscribed` in `cmo-billing.service.ts` (`overview.subscriptionActive`): Cuso works while his Project has an active CMO subscription (a scheduled cancel counts until the period ends), while he is in free hiring, or while he holds Tester credits that are not used up; otherwise he is paused, even when the Organization credit pool has credits. The gate holds back his turns (`requireSokoBotTurnFunding`, reason `cmo_paused`), scheduling and publishing, production and his context packet's Execution line. In the app the paused banner says why (`components/app/paused.tsx`): "Subscribe" starts the monthly plan checkout when the Project has no subscription, "Fix payment" opens Polar's portal for owners and admins when it is past due; Settings offers "Subscribe" to a Cuso without one, and a Cuso with Tester credits keeps them. One who runs out of them before his plan is approved is paused while still hiring (free hiring never covers him), so a hiring step's refusal offers "Subscribe" too (`subscribeOffer` in `paused.tsx`), never a top-up. A tester on Core's `CMO_SUBSCRIPTION_SKIP_ALLOWLIST` also gets "Continue without a subscription (testers)" (`SkipSubscriptionButton`, shown when `billing.maySkipSubscription`) under the plans on Subscribe, beside the paused banner's Subscribe and on those refusals; it posts `/v1/cmo/projects/{projectId}/skip-subscription`, which gives the Project Tester credits, and refreshes the overview. A hire grants no credits: until the strategy is approved, Cuso's own turns are free hiring (`isCusoInFreeHiring` in `cmo-billing.service.ts`, decided where `sokoBotPayer` in `soko-bot-billing.service.ts` resolves his payer): they are not charged and start in an organization with no credits. Members' own Jobs, image jobs and Tasks in his Project are charged as before. From approval he is paused until a plan is paid; nothing between approval and the checkout starts a Cuso turn. Once the plan is approved, Core starts one background run that writes every piece and, for a format with a picture or video, its `visual` (what it shows) and `visualFileIds` (the brand pictures it is made from) (`apps/core/src/services/cmo-production.service.ts`). Its brief holds the Brand Brain's named customers, results and reviews (`cmoProofPoints`), which Cuso's context otherwise sums up. Core makes the media, not Cuso: `cmo-media-maker.service.ts` starts each piece's picture once (a job key names its version, piece, slot and visual, so racing callers start one job and a new visual starts over), at most three at a time per the studio's limit, from the visual and the brand pictures, makes a video by animating a still made from them, puts the file on its post (or a file piece's `mediaFileIds`) and schedules a post with media on a connected network. A settled job moves the month on at once (`nudgeCmoMonth`); a slot that fails twice goes back to Cuso for a new visual. Cuso's own runs may not call `generate_image` or `generate_video`; the owner still can in chat. A pending piece whose words are written and whose media Core is making needs no run, and a `wait_for` follow-up counts as a working run. A Soko Bot's post in a month is refused when it repeats another post's message (`nearDuplicatePost`, word overlap without the month's everyday words) or carries a picture already on another post. The plan review allows at most four videos a month. Core decides when a piece is ready and starts another run for anything missing, at most four a day (`/sync/cmo-production`, every ten minutes; locally call it yourself). The calendar must hold the plan's mix and its content pillars, each pillar with a share, every entry naming one (the plan review checks both), so making it in one go keeps the ratios. Every production run's brief carries the writing skills for its networks in full (`writingSkillsBrief` in `@sokosumi/soko-bot`: brand voice, post formatting, hooks and endings, one skill per network, ads, newsletter and SEO); every turn's context lists them (`writingSkills`), and Cuso opens one with `read_writing_skill` before he writes a piece in chat; admins read them at `/admin/writing-skills` in Sokosumi. Once the month is made, the month review (`cmo-month-review.service.ts`, stored in `marketing_strategy.monthReview`) reads every piece: Jev says which pillar it is about, whether it follows each judged rule of its skill (one question per rule, only the rules for its format) and whether it sounds like the Brand Brain's voice; rules that count characters or items are checked in code (`cmoCountedProblems` for files, the save check for Social posts), because Jev cannot count. Each read is charged to the bot's payer at its metered cost (`recordSokoBotCheckUsage`, once per version and round). One rewrite run gets the pieces still to come that miss a rule, the voice, or (when a pillar's made share is more than seven points off its plan) their pillar, each with the exact reason; Jev reads the month again after it, and nothing is rewritten twice. Strategy shows each pillar's made share beside its planned one, and the Calendar filters by pillar. Social pieces are the approved version's Social posts; every other piece (an article, a page fix, ad copy, a newsletter issue) is saved with `save_strategy` part pieces and written by Core as a Markdown file in the Project's Files (`marketing-strategy-files.service.ts`), which CMO's piece sheet opens through `/v1/cmo/projects/{projectId}/calendar/{id}/text`. The app's Calendar page (`/calendar`) shows every piece as a card by week, filtered by network or pillar; a piece opens only once it is made (`pieceMade`: scheduled or out, or written with its picture or video), and until then its card says only that it is being made. The sheet steps to the next made piece (arrows) and can pause a piece. The app has no Up next column; Cuso's scene loops at the bottom of the sidebar (`CusoStatus`), and every page leads like a hiring step. "Your Cusos" shows in the sidebar only when the person has another Cuso. Strategy holds the plan only and links there. Pictures are JPEGs (Instagram takes nothing else), made from the brand's own pictures (`brandPictures` in Cuso's context: the page screenshots first, then the photos from its pages, all saved as JPEG by the brand capture). Carousel formats list their slide counts in `CMO_CHANNELS`; Core makes each slide from the one visual, and Instagram publishes two or more images as one carousel. The daily run then fills gaps, answers comments and checks the news last. Reading the web blocks post changes for the rest of a run, so news changes only the calendar, and the next production run makes the piece. The chat opens on one welcome once hired: the overview's `hiredAt` (the first approval, read from the first production run's id because a later approval clears the earlier one) hides the hiring messages and cards, which the owner already went through. Making the month shows in the chat as one progress card (`overview.production`, linking to the Calendar); every report a production run files is stored as kind `production` (`reportCmoUpdate`, whatever kind Cuso gave it), left out of CMO's chat and shown in Sokosumi's chat as its headline alone.
- **Strategy and measurement.** The strategy is one sentence (who, positioned as, how they find you, the offer) built on a funnel; each stage says who runs it (Cuso, the owner, or both) and whether its number is measured or estimated. Every first plan starts at the All-in pace and Cuso suggests an ad budget; the owner can change either, and a pace change swaps the plan for a re-planning screen until the new one lands. Launch and Channels connect Google Ads or Meta Ads to Cuso's Project (`/v1/cmo/projects/{projectId}/ads/*` in `cmo-ads.service.ts`, back through `/ads/callback`, `/ads/choose` when the login reaches several accounts). Cuso writes a google_ads search piece with `searchAd` (kept on its `marketing_strategy_file` row); an owner or admin presses Launch, and Core builds the Google campaign from it and starts it. Core refuses any start that takes running campaigns past the approved plan's ad budget a day (monthly / 30) or uses an account in another currency. Cuso never starts an ad himself; Meta campaigns are not created from CMO yet. A launched search ad targets people in its `location` (Google's presence setting; an ad without one is refused), caps a click at Cuso's `maxCpc` and never above a third of its daily budget (`cmoMaxCpc`), and excludes `CMO_NEGATIVE_KEYWORDS` (jobs, pirated copies) plus Cuso's `negativeKeywords`. Links in Cuso's posts to the owner's site get UTM tags (`tagOwnLinks`: the network, `social`, `cmo-YYYY-MM`). Weekly reviews end with a verdict (hold, fix, test, investigate) and learnings on their report; the next turns read the last four as `weeklyLearnings`. The owner connects Google Analytics, Search Console and, for a Shopify shop (the Project's `sitePlatform`, read once from the homepage), Shopify on the Plan step's "How we know it works" tab. These connect to Cuso's own Soko Bot through the generic Composio integration path (`/v1/cmo/projects/{projectId}/measurement/{provider}/connect` and `/finalize`, back through `/measure/callback`), and Cuso reads them with `run_integration_tool`.
- **Competitors.** Competitor monitoring is a Project feature Sokosumi owns ([ADR 0072](../../docs/adr/0072-competitor-monitoring-is-a-project-feature.md)): the list, the weekly check, the signals and the feed live in Core's `competitors.service.ts`, `competitor-check.service.ts`, `competitor-feed.service.ts` and `competitors-overview.service.ts`, behind `/v1/projects/{id}/competitors`, where any other Project turns the check on itself. Every Soko Bot carries `check_competitors` and `save_competitor_feed` on a Project whose check is on (`soko-bot-runtime/competitors.ts`); Cuso always carries them, on his own Project. What is CMO's sits on top in `cmo-competitors.service.ts`, and CMO reads and writes through `/v1/cmo/projects/{projectId}/competitors`, a thin layer over the same services. A Cuso's Project tracks up to five competitors (`tracked_competitor`). Core fills the list from the Brand Brain whenever Cuso saves it (the market map's players first, then its competitors list); members add, change and remove them through `/v1/cmo/projects/{projectId}/competitors`, and research never changes or brings back one a member touched. Once a week per paid Cuso with an approved strategy (`/sync/competitors`, hourly; locally call it yourself) Core checks each one in code, not through Cuso (`runCusoCompetitorCheck`, then `competitor-check.service.ts`); a newly paid Cuso's first check, and his watch run after it, start on the CMO production sync within ten minutes of payment (`keepCusoFirstCompetitorCheck`, which retries the watch run for an hour), not on the hourly one: its homepage and pricing page, each read twice so rotating banners drop out, compared line by line with last week's reading with dates, times and counters blanked and prices kept; a small model (`google/gemini-3.8-flash`) words a real change in one line and calls the rest noise, and a moved price on the pricing page is always kept. News comes from Exa for the last seven days, without review, comparison and job sites, how-tos and listicles, and the same model keeps one article per real event. Ads come from Meta's Ad Library (ads shown in the EU) and need `META_AD_LIBRARY_ACCESS_TOKEN` (a user token of an identity-verified Meta account on an app with the Ad Library API); without it the source reports `not_configured`. Instagram numbers come from business discovery through the owner's connected Instagram account, only for business accounts. Each finding is a `competitor_signal` row with its source's title, publisher, address, date and own words (`quote`), never edited. A check costs 3 credits per competitor (15 a week for five), charged once to the Cuso's payer; without credits it does not run. After each check Core starts Cuso's competitor watch (`startCompetitorWatchRun`, one run per check, retried on later syncs for two days, brief `cmoCompetitorWatchBrief`): he reads the signals with `check_competitors` and saves "This week" with `save_competitor_feed`, one item per move: facts (one sentence each, citing the signals that back it, support strong or weak), what it means for the business and one suggested move; a quiet week saves no items and lists what is still open. Core checks a save before it keeps it and refuses it whole otherwise: every cited signal is the Project's and about that competitor; no fact, meaning, move or open question has a number its signals (or, for meaning and move, the Brand Brain) lack; nothing names Sokosumi; each item's meaning names its competitor and no two items say the same, and a move that names a social network uses one the business has connected or says to connect it first (`cusoFeedProblems` in `cmo-competitor-feed-check.ts`, CMO's own rules on top of the Project feed's); and Jev reads each fact against its signals (below 0.35 refused, a strong one below 0.7 must be marked weak) and each meaning and move for claims about the competitor its signals do not make, refusing anything it leaves unanswered. Core marks the big moves (price changes and pricing news, then launches, then ad bursts; for news it goes by the event the news model labelled, `raw.event`, where launch, pricing, funding and acquisition are big, never by the wording), puts them first and posts each to Cuso's room once, from the checked feed: every fact with its sources' title, publisher, link, date and own words, the support when weak, what it means for you and the move; Cuso's own answer stays silent. "Add to strategy" on a move (`POST /v1/cmo/projects/{projectId}/competitors/feed/{itemId}/strategy`) patches the strategy through the same path as a typed change, once per move, and the monthly strategy reads the last month's moves as `competitorMoves`. The CMO evals `cmo-competitor-feed`, `cmo-competitor-quiet-week` and `cmo-competitor-second-hand` (a move known only from someone else's notice is marked weak) seed a week of signals in the lane. The Competitors tab (`/competitors`, `components/app/competitors-page.tsx`, `GET /v1/cmo/projects/{projectId}/competitors`) shows the market map with the business and the competitors still watched, "This week" (each fact with its source note, "Partly backed" for weak support, what it means for you, the suggested move with "Add to strategy", and what is still open), the Instagram scoreboard (an empty cell is no data; with no numbers at all the table is left out), each competitor's top posts with "Ask Cuso for ideas", everything the checks stored, and the watch list (add, edit, remove; a refusal shows beside what was pressed). A source note is a native popover on its chip (`Sourced`): hover, press or Enter opens it, Escape or a press elsewhere closes it, and it sits in the top layer so the table never clips it. A move of a competitor no longer watched leaves the feed, and a fact whose signal is older than the page keeps (35 days) says so.
- **SEO.** The SEO tab (`/seo`, `components/app/seo-page.tsx`, `GET /v1/cmo/projects/{projectId}/seo`) is outside the strategy and its calendar; the seo channel's status is `tab`, so a strategy never plans an article or page fix. While the Project is paid for, the CMO production sync keeps one weekly full audit of the brand's site on Core's SEO monitor (`cmo-seo-audit.service.ts`: 750 credits, the subscription is the owner's approval, Monday 06:00 UTC, a first audit at once unless that Run is under two days away, a new monitor once its 31 Runs are used, paused while unpaid, a week skipped when the Project's credits cannot cover it). The tab shows the latest audit, the page changes to do (the audit's own fixes and Cuso's, each with the exact new text; Done is checked against the next audit), article suggestions ("More article ideas" and "Write it" start a Cuso turn), keyword search (DataForSEO Labs keyword suggestions, 25 a day, a topic reused for a week) and Search Console from Cuso's own Google connection. Core attaches every number on a suggestion itself, with its source and date, and refuses one it has no data for. The audit's texts come from the SEO service with its check ids and its own wording; `src/lib/seo-copy.ts` words them for the owner where the tab shows them (ids out, a short lead with the rest under "More detail"), and Core's data and what Cuso reads stay as the service wrote them. In chat Cuso uses `read_seo`, `research_keywords`, `save_seo_suggestions` and `check_search_rankings`, which asks the SEO service for positions as a Core-approved check and answers in a follow-up once its report is imported (skill `cmo-seo`).
- **Server-side Sokosumi.** CMO holds no database. Its server reaches Sokosumi through Core's OAuth provider and `/v1`. Hiring Cuso asks where he goes: a new organization named after the website (the default), or any organization the person belongs to ("Where" on the hire form, shown only to a person with organizations; never the personal workspace). Every hire creates a new Project, and an organization may hold several Cusos, one per Project ([ADR 0065](../../docs/adr/0065-a-cuso-hire-goes-into-a-new-or-an-existing-organization.md)). Any member may hire; a hire into an existing organization leaves its name, plan and the person's preferred organization alone, and Core checks the hirer's Seat before creating a Project; an empty organization can hire, because hiring is free. A person may have one unpaid Cuso at a time (a live Cuso they hired whose Project never had a CMO subscription and never got Tester credits): a second hire is refused with `cmo_unpaid_cuso`, whose `unpaidCuso` names him, and the hire form links to him. CMO is invite-only for now: only a person whose verified Sokosumi email, or its `@domain`, is on Core's `CMO_HIRE_ALLOWLIST` may hire (an unverified person on it sees the invite-only page, and keeps every Cuso they already have), and Core refuses anyone else before creating anything (`cmo_hire_not_allowed`), because every hire's research and plan are free. `GET /v1/cmo/cusos` answers `mayHire` beside the Cusos; without it the picker leaves out "Hire a new Cuso", and the hire form (no Cuso, or `?hire=1`) becomes the invite-only page (`SignedIn` with `inviteOnly`). Everything else stays open to whoever works with a Cuso. Core declares each refusal with a `kind` (`cmo_hire_not_allowed`, `organization_seat_required`, `cmo_unpaid_cuso`, `organization_limit_reached`, `organization_membership_required`), and the hire form names its reason. Cuso is that Project's shared Soko Bot: every member of the organization works with him in his shared room, and only its owners and admins approve the strategy ([ADR 0061](../../docs/adr/0061-cuso-is-a-shared-project-bot.md)). Core keeps no CMO record: Cuso is found as a Project's shared bot on CMO's version, one per Project ([ADR 0062](../../docs/adr/0062-cmo-keeps-no-data-of-its-own.md)), and `GET /v1/cmo/cusos` lists every live Cuso the person can use, newest first. The home page (`home.tsx`) opens the Cuso the address names (`project`), else the one last opened on this device (the `cmo-last-cuso` cookie, written by `proxy.ts` for an address naming an accessible Cuso and by the hire action), else the only one, else the **Cuso picker**, else the hire form; an address naming a Project the person can't use opens the picker or hire form. `?cusos=1` ("Your Cusos" in the account menu on the hire form once the person has a Cuso, while hiring and in the sidebar) opens the picker, `?hire=1` the hire form. Sokosumi's preferred organization plays no part. From there every Cuso action names that Cuso's Project (`home.tsx` binds the rendered overview's `projectId` to each action; they call the `/v1/cmo/projects/{projectId}/…` routes), and provider callbacks (ads, measurement, social connections) carry it as `project` in their return address, so a workspace switch in Sokosumi never moves a flow to another Cuso. Start over (Settings, or the account menu while hiring; `POST /v1/cmo/projects/{projectId}/start-over`) archives that Cuso and cancels his unsent posts (for a subscribed Cuso, Core first ends his subscription at Polar, at once and without a refund, and writes off his Project credits; the confirmation says so, and nothing ends when Polar cannot be reached), then opens the hire form with a new organization selected, even when other Cusos remain (a person who may not hire gets the picker, which is the invite-only page when none remain); his organization and Files stay, and his room is renamed after his website ("Cuso · acme.io"). Hiring into a new organization again before any plan of his was approved stays in that organization, renamed after the new website, so the earlier chat sits beside the new Cuso's (`organizationLeftWhileHiring`); a retry after a failed hire reuses its empty organization. An existing organization is never reused or renamed. Only a person without a valid first and last name gives one first.
- **CMO Projects are read-only in Sokosumi** ([ADR 0066](../../docs/adr/0066-cmo-projects-are-read-only-in-sokosumi.md)): CMO writes only through `/v1/cmo/**`, and Core recognises CMO by the token's client (`CMO_OAUTH_CLIENT_ID`), never by its redirect URI, because anyone can register a client with CMO's callback.
- **Project top-ups.** A Cuso with an active CMO subscription (`billing.status === "active"`) gets "Top up" on the out-of-credits banner, an out-of-credits refusal and the Credits card in Settings (`TopUpButton` and `topUpOffer` in `src/components/top-up.tsx`); a Cuso without one gets none. `startTopUp` asks Core (`POST /v1/cmo/projects/{projectId}/top-up`) for Polar's checkout with the top-up packs and sends the browser there; the person comes back to `/?project=<id>`, and the credits land on that Cuso's Project when Polar's `order.paid` reaches Core ([ADR 0068](../../docs/adr/0068-cmo-sells-its-plans-through-polar.md)). CMO never links to Sokosumi's billing page.
- **Plan change and billing portal.** Settings' Subscription card (`src/components/app/subscription-card.tsx`) shows owners and admins (`billing.viewerCanManage`) the pending downgrade, the other plans of the Cuso's interval and "Manage billing"; other members see the plan alone. A plan change (`POST /v1/cmo/projects/{projectId}/plan`) is confirmed first: an upgrade applies at once and Polar charges the prorated difference, a downgrade waits for the next renewal. Core writes Polar's answer (the new tier, or the pending one) onto the subscription before it answers, so the card shows it at once; an upgrade's extra credits still come only with `order.paid`, which the app's overview poll picks up. "Keep my plan" beside the pending downgrade sends the current tier, which drops the downgrade at Polar. It is offered only while the subscription is active and not cancelled. "Manage billing" (`POST /v1/cmo/projects/{projectId}/portal`) opens Polar's customer portal for the organization, which links back to Settings; plan changes are off there ([ADR 0068](../../docs/adr/0068-cmo-sells-its-plans-through-polar.md)).
- **Time zone.** Cuso's routines run in the owner's time zone: the hire form sends the browser's zone (`timeZone` on `POST /v1/cmo/onboarding`), and Settings shows it with a one-tap switch to the browser's zone and a list (`TimeZoneSetting`, `PUT /v1/cmo/projects/{projectId}/time-zone`, which moves his routines and their next runs). It is the bot's `ingestTimezone`; a Cuso hired before this stays on Europe/Berlin until someone changes it.
- **What Cuso is doing.** While Cuso runs any turn (a chat message, hiring, a rhythm, the month's production) the overview's `activity` holds the step he is on, in CMO's words, and the model's latest reasoning summary (`cmoActivity` in `cmo-hiring.service.ts`; labels in `apps/core/src/lib/soko-bot/cmo-step-labels.ts`, never a tool's name or a Sokosumi feature). The chat shows it in place of typing dots (`Working` in `src/components/cuso-trace.tsx`), and the Plan wait shows the reasoning line under its title; the Research wait shows his steps only, because his thinking there reads as confused to someone who has just met him. The sandbox runner posts each step's summary to Core as the step ends (`/v1/soko-bot-runtime/turns/{id}/reasoning`); `activity` reads it from the runtime's log, so it shows before the turn is next reconciled. Under each reply, "How I got here" folds the steps and summaries Core keeps on the message (`metadata.reasoning`: a part with `kind: "step"` is a step, one without a kind a summary). Everyone who works with a Cuso sees his summary; a personal Soko Bot's stays with its owner. With no summary, only the steps show.
- **Two languages.** Cuso writes to the owner in the language of their latest chat message, and every piece in the strategy's `contentLanguage`, the audience's: a calendar entry's title, brief and story and the pillar names belong to the piece; the rest of the strategy explains it to the owner. Core ends every Cuso turn's message with the owner's latest chat message, its language as Jev names it, and that rule (`withCmoReplyLanguage` in `apps/core/src/lib/soko-bot/cmo-reply-language.ts`), because a follow-up, a rhythm or an event has no owner message of its own; while a strategy waits for approval, `save_strategy` asks Jev whether a calendar save's new titles are in `contentLanguage` (`cmoCalendarLanguage`).
- **Posts made on request.** A Social post Cuso makes in chat outside the month (a video with its X draft, say) waits as `NEEDS_APPROVAL`. Core attaches to each report what its turn made, read from the turn's tool calls (`cmo-drafts.service.ts`, `cmoReportAttachments`): the Social posts it created and did not drop again, or, when it made none, the pictures and videos it fetched from the studio. The overview's `updates[].posts` and `updates[].media` carry them and `drafts` lists every post that waits. The chat shows them under the report (`components/app/draft-post.tsx`): the picture or video plays in place, and the owner approves, rewrites or declines the draft there; the Calendar leads with the same cards under "Waiting for you". Approve (`POST /v1/cmo/projects/{projectId}/drafts/{postId}/approve`) keeps a planned time and otherwise sends the post out two minutes later, so it can still be stopped ("Don't post it"); a network that is not connected refuses it and the draft stays. Decline cancels it; `PATCH …/drafts/{postId}` changes its words. A turn files one report card per kind: reporting again rewrites the card (`reportCmoUpdate`). A follow-up run that filed its card posts nothing else, and a turn that reported never ends on "Nothing was changed in this turn." (`buildActionResponse`).
- **What Cuso makes and hands on in the chat.** What a chat turn of Cuso's starts shows in the thread where he started it (`MadeInChat` in `src/components/app/chat-work.tsx`, placed by `buildThread`), and the app's poll reads `GET /v1/cmo/projects/{projectId}/chat-work` beside the overview (`listCmoChatWork` in Core's `cmo-chat-work.service.ts`), so each one moves on without a reload and is still there after one. A picture, video, talking video or voice-over is a frame that says it is being made, then the file itself, playable, with a Download link to its public address. A file he wrote (`upload_file`) is a card with Read it and Download. Work he gave a Coworker (`create_task`, `assign_task`) or a hired Agent (`hire_agent`) is a card that names who has it and where it stands: working, needs an answer (with the question and an Answer button that fills the composer), done (the start of the result, its files, and Read it) or not finished. Read it opens the full words in the card (`GET …/chat-work/{id}/text`). Core reads all of it from Cuso's tool calls and the records they made, never from his words: a styled picture is ready only once its style check passed, a job still not made after an hour shows as failed with "Ask Cuso to try again", a Task with no Coworker on it and a file the owner deleted are left out, and a Task made and then assigned shows once. Nothing here links to the Content Studio, Files, a Task or a Job page.
- **Cuso's words and rules (cmo-v4).** From cmo-v4 on, nothing Cuso reads about himself or his tools calls him Soko Bot or names a Sokosumi place: his identity line and persona, his base prompt, the shared skills in his own wording (`cmo-social-posts`, `cmo-long-work`, `cmo-code-tools`, `cmo-agent-jobs`, `cmo-ask-coworker`, `cmo-newsletter` in `packages/soko-bot/src/versions/cmo-v4-skills.ts`) and every tool description (`cusoToolDescription` in `packages/soko-bot/src/cmo-texts.ts`, handed to both runners as `toolDescriptions`). He is told to name what he made and never to link it, because the chat shows it. `cmo-v4.test.ts` reads everything he is told and fails on a forbidden word. The version drops five tools with no place in CMO (`manage_reminder`, `list_chats`, `read_chat`, `link_tasks`, `set_task_parent`). Three rules hold for every Cuso, whatever his version, in Core: a Task he creates or assigns goes to a Coworker, never to a person or to nobody (`refuseCusoPersonTask`); he may not change one of his built-in rhythms, so a reminder is a schedule of its own (`keepBuiltInRhythms` on `updateSokoBotSchedule`; a person still changes or pauses one); and a follow-up of his that changed nothing ends silent (`buildActionResponse`).
- **Evals.** A change to how Cuso behaves (his skills, prompts, tools, version or model, or Core's checks on his plan and posts) runs the CMO evals before it merges, and new Cuso behaviour ships on a new Cuso version. See [evals](../../docs/agents/evals.md).

## Run CMO locally against a local Core

Cuso needs Core's CMO routes and migration, so a branch that changes them runs against its own Core and database, never the shared dev Neon branch.

1. **Database.** Create an empty local Postgres database and point `apps/core/.env` and `packages/database/.env` at it. On Postgres 14/15, `prisma migrate deploy` fails on an old migration; create the schema from the Prisma files instead: `CREATE EXTENSION pg_trgm;`, then apply `pnpm exec prisma migrate diff --from-empty --to-schema prisma --script` (from `packages/database`) with `psql`. Seed test accounts with `CLOUD_AGENT_DB_FORCE=1 node scripts/agent-db/seed-auth-fixtures.mjs` (`alice@sokosumi.test` and the others, password `Password123!`).
2. **Core and Web.** Core's `.env` needs `SOKO_BOT_ENABLED="true"`, `SOKO_BOT_RUNTIME_ADAPTER="in-process"` and an `AI_GATEWAY_API_KEY`, with `BETTER_AUTH_URL` and `WEB_APP_BASE_URL` on your local ports. Web needs Node 26 (`.nvmrc`, `apps/web` `engines`) and `CORE_APP_BASE_URL` / `NEXT_PUBLIC_CORE_APP_BASE_URL` on that Core.
3. **CMO's OAuth client.** Signed in as a test account, `POST {core}/auth/oauth2/create-client` with `token_endpoint_auth_method: "client_secret_basic"`, `grant_types: ["authorization_code", "refresh_token"]` and `scope: "openid sokosumi:api offline_access"`. Better Auth only registers `https` redirect URIs on non-loopback hosts for web clients, so register a placeholder, then set the real callback on the row in your local database: `UPDATE "oauthClient" SET "skipConsent" = true, "redirectUris" = ARRAY['http://localhost:<cmo port>/api/auth/callback/sokosumi'] WHERE "clientId" = '<client_id>';` (authorize matches the URI exactly). Set Core's `CMO_OAUTH_CLIENT_ID` to this `client_id` and restart Core: every `/v1/cmo/**` write from another client, an API key or a session gets 403 `cmo_client_required`, and none is allowed while it is unset.
4. **CMO.** `apps/cmo/.env.local` holds `BETTER_AUTH_URL` (CMO's origin), a random `BETTER_AUTH_SECRET`, `CORE_APP_BASE_URL`, and the client's `SOKOSUMI_OAUTH_CLIENT_ID` / `SOKOSUMI_OAUTH_CLIENT_SECRET`. Start it with `PORT=<cmo port> pnpm dev`.

The in-process runtime has no sandbox, but it runs Cuso's read-only web tools (`web_search` through the AI Gateway, `web_fetch`) itself, so Cuso reads the real site locally too. Shell and workspace tools stay sandbox only.

To run a CMO rhythm now instead of waiting for its schedule, move its `nextRunAt` into the past (`soko_bot_schedule.systemKey` is `cmo-daily-run` or `cmo-weekly-review`; the column is UTC) and call `GET {core}/sync/soko-bot-schedules` with `Authorization: Bearer <CRON_SECRET>`.
