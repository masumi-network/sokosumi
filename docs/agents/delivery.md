# Commits, CI, and pull requests

Required when the matching trigger in [AGENTS.md](../../AGENTS.md) applies.
Commands and backticked paths are relative to the repository root unless stated otherwise.

### Git hooks

Husky runs `pnpm precommit` (`pnpm check && pnpm effects:check && pnpm typecheck`) before each commit. Expect 20–30 seconds with a warm Turbo cache and 1–2 minutes on a fresh checkout or cloud session, where `typecheck` starts cold. Let it run: it covers the local `Biome` and `Typecheck` checks, while CI's `Biome` job also runs the full `no-direct-effects` suite against the base SHA (`EFFECT_BASELINE_BASE_REF`) to reject any baseline growth.

`git commit --no-verify` and `HUSKY=0` exist for the case where the hook itself is broken — a missing binary, a worktree without `node_modules`. Fix the cause and commit normally. Passing the checks by hand first is not a reason to bypass the hook: the bypass is indistinguishable from hiding a failure, and only the hook's own run proves the tree is green.

The hook checks the whole working tree, not only the staged files. An unstaged edit with a type error in another file blocks an unrelated commit, and the last line says only that the pre-commit script failed. Search the full hook output for `error TS` to find the file.

After a merge or pull, `.husky/post-merge` reinstalls when `pnpm-lock.yaml` changed and regenerates Prisma when `packages/database/prisma` changed.

In a fresh worktree the hook fails with `Command "prisma" not found` until `pnpm install` has run there. Install (about 30 seconds) rather than committing past it with `--no-verify`: the failure is the worktree's `node_modules`, so every later check is blind too.

## Commit & Pull Request Guidelines

### Commits

Follow [Conventional Commit](https://www.conventionalcommits.org/en/v1.0.0/) syntax:

```
feat(auth): add refresh token (#1234)
fix(ui): resolve button alignment issue
docs(readme): update setup instructions
```

### Branches

- **Sokosumi Tasks**: When implementing a Task, the branch name MUST start with the Task identifier (lowercased), followed by a short kebab-case description. For example, for `SOKD-109` name the branch `sokd-109-xxx-xxx-xxx`. Prefer `task.identifier` from `sokosumi --api-url https://api.sokosumi.com tasks get … --json` (mainnet — this repo's tracker) when available. See [issue tracker](./issue-tracker.md).
- **One branch per PR.** Start every new PR on a branch name no earlier PR used. Preview `DATABASE_URL*` env vars are scoped to the git branch and owned by one PR (`scripts/ci/preview-resources.ts`), so a reused branch fails `/deploy` with "owned by another workflow" until the old PR's preview is cleaned up. Never push a branch under `preview-fork/`: the preview workflow owns it and force-moves `preview-fork/pr-<number>` to a fork PR's approved head SHA.

### Pull Requests

> [!IMPORTANT]
> **PR titles MUST follow [Conventional Commit](https://www.conventionalcommits.org/en/v1.0.0/) syntax — this is enforced by the `Validate PR Title` CI check and a non-conforming title will fail the build.** This applies to _every_ PR title, including ones auto-generated by AI/cloud agents (e.g. the Claude Code "Create PR" flow).
>
> **Set the PR title to the primary commit's subject line verbatim** — it is already a Conventional Commit. Do NOT invent a new descriptive sentence or rely on a generated summary; that is what produces non-conforming titles. If you create or rename a PR, set the title yourself in this format.
>
> **Format**: `type(optional-scope): description` (lowercase `type`, no trailing period).
>
> **Allowed types**: `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`, `revert`.

| ✅ Valid                                              | ❌ Invalid                                                    |
| ----------------------------------------------------- | ------------------------------------------------------------- |
| `feat(core): add agent rating read endpoints for web` | `Add endpoint for fetching authenticated user's agent review` |
| `fix(admin): remove duplicate Organization header`    | `Remove duplicate Organization header`                        |
| `feat(auth): add refresh token`                       | `Make FormSection title optional`                             |
| `chore(deps): pin biome version`                      | `Update deps`                                                 |
- **Required status checks** on `main` (ruleset `Default Branch`): `Build`, `Validate PR Title`, `Biome`, `Test Core`, `Test Core PostgreSQL`, `Test Core PostgreSQL split layout`, `Test Packages`, `Test Web`, `Test CLI`, `Test CI config`, `Typecheck`, `Swift lint and format`, `Xcode test`. Read the live list with `gh api repos/masumi-network/sokosumi/rulesets/3855070 --jq '.rules[] | select(.type=="required_status_checks") | .parameters.required_status_checks[].context'`. Deleting or renaming the job behind one of these blocks every PR on a check that never reports, so update the ruleset in the same change.
- **Land a PR through the merge queue: `gh pr merge <n> --auto --squash`.** The agent that opened the PR merges it unattended; the ruleset requires no approving review, so the required checks are the gate. `main` has a merge queue (ruleset `Default Branch`), so a PR no longer has to be up to date with `main`; do not update branches to unblock a merge. Once every required check on the PR head passes, GitHub queues the PR, builds a temporary `gh-readonly-queue/main/pr-<n>-…` commit of `main` plus the PRs ahead of it, and runs the required checks there (`merge_group` event). It squash-merges when they pass and drops the PR from the queue when they fail; fix it and run the command again. Every workflow behind a required check must run on `merge_group` and report the same check name (pinned in `scripts/ci/__tests__/js-caches.test.mjs`), or every queued PR waits out the 60-minute timeout. `gh pr view <n> --json mergeStateStatus,autoMergeRequest` and the PR page show the queue position.
- **Advisory status checks** in `.github/workflows/ci.yml`: `Test Local env`, `Test Agent db`, `Lint DESIGN.md`, `Test Core PostgreSQL split layout`. They are **not** in the ruleset; a red advisory job does not block merge. CI does not run web's `*.webkit.test.*` files: installing their browsers' apt packages stalled on the Ubuntu mirror. Run them locally with `pnpm --filter web test:webkit` when you change the chat transcript or the layout they check. `Test CI config` runs on Markdown, `package.json`, and CI-file changes, so the doc-script check still executes on docs-only PRs. `Lint DESIGN.md` runs `@google/design.md` (pinned; the spec is alpha) on `apps/web/DESIGN.md` and `apps/cmo/DESIGN.md` when either changes or when `ci.yml` or `js-paths-filter.yml` does, and fails on errors and warnings.
- **Path-gated jobs skip, they do not start.** Every JS job (`Build`, `Biome`, `Typecheck`, and each `Test …` leg) gates with a job-level `if:` on its path filter in `.github/js-paths-filter.yml`. A skipped job gets no runner, still reports its check name, and the ruleset accepts a skipped check. Keep each leg a named job, not a matrix entry: a skipped matrix reports one placeholder name that satisfies no required context. `Test Web` and `Test Core` each run their whole unit suite in one job, through `turbo run test:ci` so an unchanged suite replays from the remote cache; `Test Core PostgreSQL` is Core's second job, beside `Test Core` under the same `core` filter: it applies migrations, checks drift and runs Core's PostgreSQL suites. `Test Core PostgreSQL split layout` runs the same suites beside it on the new layout (`shared`, `mainnet`, `preprod`, built by the test-only `packages/database/scripts/split-network-layout.sh`); it runs every file not listed in `apps/core/src/test/split-layout-pending.txt` and fails on any failure, then fails if a listed file passes. A file that fails there only is listed with the ticket it waits for; the line is in the PR's diff. Do not shard them: the organization's plan runs 20 jobs at once across every repository, and shards made overlapping pushes queue for longer than the shards saved.
- **Measure CI speed with `pnpm ci:timing [workflow] [runs]`** (default `ci.yml 150`). It reads the latest completed PR runs through `gh` and prints the wall clock (run created to last job done) at p50 and p95, plus each job's waiting, setup and running time; path-gated jobs are left out. A PR that changes CI speed puts this report from before and after in its Evidence.
- **CI jobs restore caches; only `.github/workflows/next-build-cache.yml` saves one, from `main`.** A PR's cache is scoped to its merge ref, so no other PR can read it, and PR-saved pnpm stores once filled the repo's 10 GB. Build restores web's Turbopack cache (`js-next-*`). Keep new keys under `js-` so they never collide with Apple's `macOS-*` keys: `apple.yml`'s `Warm Apple caches` job (daily `17 3 * * *` plus `workflow_dispatch`) saves Mint, Swift package checkouts and Xcode's compilation cache from `main`, and deletes superseded compilation cache entries the same way. `Xcode test` and `Swift lint and format` run on pull_request and merge_group only, when Apple files changed; they restore those keys and do not run on push to main. Build env placeholders live in `.github/ci-build.env`, shared by both workflows. Caching the pnpm store (#5160) or `node_modules` (#5165) measured no faster than a registry install.
- **Judge a SHA by its newest run, not by `check-runs`.** `ci.yml` and `apple.yml` cancel a superseded PR run, and the cancelled run's killed jobs show as `failure` in the commit's `check-runs` beside the newer run's `success`. Read `gh run list --commit <sha> --event pull_request --json databaseId,name,conclusion,createdAt` and keep the newest run per workflow.
- **Draft by default**: Open new PRs as **draft** unless the author explicitly asks for a ready-for-review PR. CI (`ci.yml`, `apple.yml`, CodeQL) skips every job on a draft; `Validate PR Title` still runs. Mark the PR ready for review once the change is complete and the pre-commit checks pass: that starts CI. When `gh pr view <n> --json autoMergeRequest` shows auto-merge pending while the head SHA's validation is incomplete, run `gh pr merge <n> --disable-auto` before marking ready. Merge or enable auto-merge only when every required check on the current head has completed and passed across CI, Apple, and the title check: `gh pr checks <n> --required` shows each as `pass`, or `skipping` from a post-ready run for an intentional path skip. One workflow finishing is not enough. A draft's skipped required checks count as passed, and rulesets ignore `workflow_dispatch` jobs, so `gh pr ready` followed at once by `gh pr merge --auto` can merge before CI completes (#7374); every merge to `main` production-deploys each app it affects ([deploys](./deploys-and-observability.md)).
- **Auto-merge lands the first green push.** Put the whole change in the first push. A later push to an auto-merge PR is itself a merge trigger: turning a red check green merges it unreviewed, so when `gh pr view <n> --json autoMergeRequest,reviewDecision` shows auto-merge on and no review, ask the author before pushing (`gh pr merge <n> --disable-auto` holds it). If the PR merged without your commit, cherry-pick it onto a new branch from `origin/main` and open a follow-up PR; `remote: … /pull/new/<branch>` in the push output means the PR is already closed.
- **Confirm each push landed.** Others merge `main` into open PR branches, so a rejected non-fast-forward push is routine. After `git push`, run `git fetch origin` and compare `git rev-parse HEAD` with `origin/<branch>`; post a review reply that cites a SHA only after they match. Before fixing review feedback, fetch and fast-forward the branch first.
- **Stacked PRs.** A multi-Task epic gets one draft PR per Task, based on the umbrella branch, stacked on the previous Task's branch until that merges. Merge `main` into a stacked branch right after its base squash-merges; the squash otherwise re-applies the base's commits as conflicts. Until any of the epic is on `main`, edit its migrations in place instead of adding rename migrations.
- **Close the upper PRs before collapsing a stack.** When a stack's commits are folded into its base branch, pushing that base makes GitHub mark every PR above it as merged into it and delete their branches, because the repo deletes merged branches. Close the dependent PRs first, then push the collapsed base.
- **Each stack layer must typecheck alone.** CI runs `Typecheck` at each stacked PR's own head, so a stack can be green at the top and red in the middle. A layer that adds a required Prisma field also updates every fixture typed as that model, in the same commit.
- **The on-switch goes in the top layer.** Layers merge bottom-up and can run in production alone for days. Put the switch that turns a feature on (a shared list, a flag, a default) in the same layer as the last consumer that must handle it. Tests in a lower layer pass an override instead of flipping the real switch.
- **Review feedback**: Treat each finding as a hypothesis. Check it against the code or the rule it cites before changing anything, fix what holds, then reply on the PR thread: what changed, or why not. A review that arrives as one summary comment (a review bot's `## <Name> review`, or a human's single PR comment) has no thread, so answer it with one PR comment that links it and covers every finding, Minors included: the commit that fixed it, or why it stays. Reply after the fix is pushed, so the reviewer can see you worked on it.
- **Title**: Follow [Conventional Commit](https://www.conventionalcommits.org/en/v1.0.0/) syntax (e.g. `feat(auth): add refresh token`)
- **Body**: write it with the `pr` skill (`.agents/skills/pr/`); the repo has no PR template.
- **Description**: Explain user-facing impact
- **Links**: Reference the Sokosumi Task identifier (and GitHub issues when relevant)
- **Verification**: List steps (e.g., `pnpm test`, `pnpm build`)
- **Screenshots**: None in PRs. Agents cannot upload to PRs or issues, and an image-only branch has no `vercel.json` to skip it, so each push starts a deploy in every Vercel project that fails at `The specified Root Directory "apps/web" does not exist`. Never push a branch to host images. For a UI change, use test output as the evidence and point reviewers at the preview (`/deploy`); show screenshots to the author in the session instead.
- **Evals**: a PR that changes how Soko Bot or Cuso behave puts `sokosumi evals show RUN_ID --markdown` in its Evidence and commits the run's summary file ([evals](./evals.md)).
- **Schema Changes**: Flag migration filenames and mention data scripts (`pnpm --filter @sokosumi/database data-migration:<name>`).
- **Preview without app changes:** `/deploy` skips a PR that changes nothing under `apps/web/`, `apps/core/`, `apps/cmo/`, `apps/cmo-website/`, or `packages/` (for example an empty commit for an e2e run). Comment `/deploy <network> --force` to deploy it anyway (same-repo PRs only); this also creates the Neon branch that `--reset-db` needs.
- **Preview database reset:** `/reset-db <mainnet|preprod>` or `/reset-db all` on a PR comment resets that PR's Neon preview branch, redeploys Core, and drops preview-only data. `/deploy … --reset-db` resets, then deploys. Full command, access, and environment rules are in the root [README](../../README.md#deployment).
- **Preview cleanup on close:** merging or closing a PR deletes its Neon preview branch, its Vercel preview deployments, and its branch-scoped preview env vars (the `closed` job in `.github/workflows/preview-deploy.yml`). The daily `Reconcile closed previews` run sweeps any it missed, and is the only cleanup for fork PRs, including their `preview-fork/pr-<number>` branch (their `/deploy` must name the reviewed head SHA, see the root README); dispatch `Preview deploy` by hand to sweep sooner. After a reopen, comment `/deploy <mainnet|preprod|all>` to rebuild the preview. Legacy previews require a separately reviewed cleanup.
