# ADR 0033: Typing rides its own ephemeral channel

- Status: Accepted
- Date: 2026-09-20

**Typing** is published by the browser as an ephemeral Ably message on a second per-room channel, `chat_typing:room_{roomId}`, granted `["publish", "subscribe"]` for every membership room. The message channel `chat_rooms:room_{roomId}` stays `subscribe`-only. Core neither reads nor writes the signal: the whole Core diff is the capability map in [`subscribe-capability.ts`](../../apps/core/src/lib/ably/subscribe-capability.ts). No endpoint, no table, no DTO.

The client publishes `{ userId, state, parentMessageId }` with `extras: { ephemeral: true }`, throttled to one heartbeat per **10s**, and an explicit `stopped` on send, on clearing the composer, on blur, and on leaving the room. Receivers expire a silent typist after **12s** (heartbeat + Ably's 2s grace) and aggregate by `userId`, so the stop event is an optimisation, never a correctness requirement.

**Why a second channel rather than `publish` on the message channel:** Ably capabilities are per channel and operation, never per event name. Granting `publish` on `chat_rooms:room_*` would let any room member publish a forged `chat_room_message`, which every client currently renders as a genuine message from whoever the payload names — live, convincing, and unpersisted, so it leaves no trace to audit. Core publishes server-side over REST with no `clientId`, so a client-side `message.clientId` guard would filter the forgery, but that puts a security invariant in a check each client has to remember; web, Apple and anything later. A separate channel makes the forgery impossible to send rather than possible to catch. The cost is one extra capability entry per membership room and one extra channel attach for the open room.

**Why ephemeral messages rather than Presence:** Ably ships ephemeral messages for exactly this ([pub-sub/advanced](https://ably.com/docs/pub-sub/advanced)), and its own Chat SDK bills typing as ordinary messages, not presence. Presence fans out n², caps at **200 members per channel** before server-side batching, costs the same per message as a publish, and auto-re-enters on reattach — so a tab that crashes mid-sentence comes back announcing that it is still typing. Ephemeral messages are exempt from history, rewind and resume, so a reconnecting client starts with an empty typing set, which is the correct state.

**Why `parentMessageId` ships always null:** it is the one piece of the payload no current behaviour needs, and normally that earns deletion. It stays because the wire is the expensive thing to change: Thread-scoped Typing is a known next slice, and a reader running an older build that met an unknown payload shape would light its room line up for a Thread reply. Shipping the field now means readers drop Thread events from day one, so the follow-up is additive on both sides rather than a flag day. The receive-side guard that ignores a non-null value is therefore deliberately unreachable today, and is what makes that true.

**What the second channel costs the token, and why Ably auth must stay on TokenRequests:** the capability is a JSON map with one entry per channel, so a second per-room channel roughly doubles chat's share of it — measured at **~69 bytes per room before, ~149 after**. A reader in 100 rooms carries about 15KB, one in 200 about 30KB.

That is fine because Core mints with `client.auth.createTokenRequest`, where the capability travels in a response body and Ably documents no size limit. It would **not** be fine over [JWT auth](https://ably.com/docs/auth/token/jwt): a JWT rides in an HTTP header and must fit its ~8KB ceiling, which a 100-room reader passes on chat entries alone. Ably's own guidance is to prefer a TokenRequest exactly when "the capability list is too large and exceeds JWT size limits".

So: **do not move browser Ably auth to JWTs without first shrinking the capability** — by collapsing the two per-room channels into one grant, by granting a namespace wildcard, or by scoping the token to rooms the client actually has open. The [TokenRequest spec](https://ably.com/docs/api/token-request-spec) states no limit at all, which is an absence of documentation rather than a documented absence of one; a server-side ceiling would have to come from Ably support.

**Why the client publishes directly:** the signal is high frequency and worthless a second later. Proxying it through Core would add a hop and a rate-limited endpoint for no safety gain once the capability is scoped to the one channel. Ably's per-connection ceiling of 50 msg/s is far above a 10s throttle.

**Scope:** every room, Channels and Directs alike. Humans only; a coworker's turn is already announced by **Thought**, and announcing it twice in two vocabularies would be worse than not announcing it. The selected room only, so the sidebar attaches nothing. Web only for now; the Apple client needs its own capability handling before it can participate, recorded as a parity row.

**Rejected:** `publish` on the existing room channel with a client-side `clientId` guard (works today, one forgotten guard away from live message spoofing); Ably Presence with an `isTyping` flag (the 200-member cap, the n² fan-out, and re-entry on reconnect resurrecting stale typists); the Ably Chat SDK (a second realtime SDK and a channel-naming scheme alongside the pub/sub one already in use); routing typing through a Core endpoint (a hop and an endpoint for a signal that expires in 12 seconds); typing in the sidebar for unopened rooms (every membership room attached and heartbeating to animate a row nobody is looking at).
