# ADR 0023: Web owns push rendering — data-only payloads, one OS-banner renderer

- Status: Accepted
- Date: 2026-08-26
- Amended: 2026-09-08

Push payloads (SOK-699) carry **data only**: the same fields as the realtime `notification_created` event (notification id, kind, `messageKey`, `messageParams`, `referenceId`, metadata). Core sets no `notification` title/body part. The web-owned service worker builds title, body, and destination href from that data, and its registration (`registration.showNotification`) is the **single OS-banner renderer**: pages trigger it for realtime events on unfocused tabs; the push event triggers it when the app is closed. The `new Notification()` constructor path from SOK-698 is deleted, not kept alongside.

**Why:** Notification text and hrefs are localized and routed web-side (next-intl, web routing helpers); Core has no web message catalog. Rendering server-side would either duplicate a string catalog into Core or move href routing into `@sokosumi/utils` — the restructuring that sank the canceled PR #3587. Two display paths (page `Notification()` + SW push) double-banner an open-but-unfocused tab; a single renderer removes the dedupe problem instead of managing it, and is iOS-correct by construction (`Notification()` never worked there; SW display is what installed PWAs support).

**Consequences:**

- The SW bundles the push-relevant message strings per locale (v1: the CHAT keys). Adding a pushed kind means adding its strings to the SW map.
- One `notificationclick` handler focuses a tab that can act on the click and hands it the target; the tag dedupes replays (one scheme when this ADR was written, two since SOK-915 — see the amendment below). With no such tab open, this slice opens the app root instead of the destination. The target carries no href, and building one in the worker would duplicate the app's routing, which is the duplication this ADR exists to avoid. SOK-876 owns that handoff. The cost is real: the no-tab case is the closed-app case push exists for, so a reader who taps a banner with Sokosumi closed lands on the app root and finds the chat themselves.
- Show/skip rule is platform-scoped. Chromium documents a focused-window exception ("you don't have to show a notification … when the user has your site open and focused", web.dev), so the SW skips display there only when a focused, visible client answers that it renders the notification itself. A same-origin tab that renders nothing (a share link, a page with the listener unmounted) does not suppress the banner. WebKit documents no exception and revokes subscriptions on violations ("pushes will always be user visible", webkit.org/blog/12945), so on Apple platforms the SW **always** displays — idempotently: a re-display carrying the same `tag` replaces the existing banner in place with no re-alert (`renotify` unset). One banner per notification, no downgrade, promise kept. Verified 2026-08-27: Firefox does **not** suppress a banner for a focused origin, so the surplus banner the Chromium-only skip accepts is real and visible there. It stands, because widening the skip trades that banner for a revoked subscription. iOS foreground behaviour and tag-replace semantics remain SOK-874's to confirm.
- Self-heal: on app open, the client checks `pushManager.getSubscription()` and re-activates when the subscription is missing or revoked, whatever the cause. SOK-876 owns this. The first slice ships the read half only: the settings card reads the subscription on mount, and nothing re-activates.
- Push data is a flat string-to-string map. Ably's REST reference calls push `data` an "arbitrary key-value string-to-string payload", and FCM's HTTP v1 API rejects nested JSON outright ("payloads such as nested JSON or integer values are not supported and will need to be strings"). Core therefore JSON-encodes `messageParams` and omits `metadata` when it is null; the service worker parses them. The field list above is unchanged, only its encoding.
- If the SW fails, nothing displays — there is no OS-rendered fallback title. **Verified 2026-08-27** on preprod: Ably delivers a push carrying no `notification` part at all, and the worker renders it. Confirmed on Firefox, on Chromium, and on an installed iOS web app. This was the least-supported assumption in this ADR, on the grounds that Ably's published channel examples all include a `notification` object; it held.
- Core ships **no** `notification` part. An earlier revision published `notification: { ttl }`, because Ably documents `ttl` inside `notification` and the research doc records `ttl: 3600` as required for Web Push on Edge/WNS, where it becomes the RFC 8030 `TTL` header. Ably defines `notification` as `title`, `body`, `icon`, `sound` and `collapseKey`, so an object holding only `ttl` carries no field Ably reads. It was dropped as undefined input and Ably applies its own TTL. If an offline device turns out to need an explicit one, `extras.push.web` is where to look, with evidence rather than assumption.
- Whether Ably accepts a `notification` carrying only `ttl` is now moot, because Core sends none. A commit message on this stack once claimed that field stopped delivery outright. **That was wrong**, and it is corrected here rather than quietly dropped: push was being delivered the whole time. The silence came from macOS, which suppresses banners while a Focus mode with Intelligent Breakthrough and Silencing is active and files them into Notification Centre instead. Ably's push notification log also appears not to record web push, so an empty log proved nothing either way.
- Activation must stop `ably@2.28.0` asking for the OS notification permission a second time. `getW3CPushDeviceDetails` opens with `await Notification.requestPermission()` (`build/push.js:194`), and `activate()` awaits `getDevice()` and `ensureInitialized()` before reaching it (`build/ably.js:3239`), so on WebKit that request lands outside the user gesture and resolves `denied` even while the stored permission reads `granted`. The web client answers from the stored permission for the duration of activation, which is Ably's own fix (ably/ably-js#2071, open since 2025-08-19 and unreleased as of `2.28.0`). Without it an installed iOS web app cannot activate at all; Chromium and Firefox are unaffected, because a repeat request there resolves from the stored permission with no gesture needed.

**Amended 2026-09-08 (SOK-915): two tag schemes, and the banner says how many are waiting.**

- There are now two tag schemes, not one. A chat notification is tagged by its room (`sokosumi-room:<referenceId>`), so a mention, a direct message and a room's counted row share one banner per conversation. Everything else keeps its notification id. The prefix exists because room ids and notification ids come from one generator, so a bare room id could equal the id of an unrelated notification and replace its banner. The replay-dedupe property survives: a replayed push for a room still carries that room, so it still replaces rather than stacks.
- The two renderers each hold a copy of two rules, because the worker cannot import from the app: which banner a notification belongs to, and which line it reads under once several messages are waiting. `push-service-worker-display.test.ts` runs the worker against the app's own functions and fails when either copy is edited alone.
- Replacing costs the reader the banner it replaced, which was the only record those messages arrived. So a chat banner speaks for the whole room: past one message it says how many are waiting there rather than naming the newest arrival.
- **Core sends that number**, as `groupCount` on the publish envelope, string-encoded for push like every other push value. The worker can query nothing, so a count worked out where the banner is shown would exist only for a tab that was open. Core sums what each unread row for the room stands for, rather than counting rows, because a room's messages are counted onto one row: four messages and a mention are five, not two. It is sent only on an unread chat row, so a row published to take a banner down carries none.
- The count deliberately does not use the row's own stored `count`. That number is what was counted onto one row, and the Notification Center still reads it; `groupCount` is the whole room. A reader whose Core predates the count gets the stored params, which is the line the banner showed before there was one.

**Rejected:** Core-rendered title/body (locale + catalog duplication in Core); keeping `new Notification()` beside the SW with tag/skip dedupe between two permanent paths; shared-package href routing (PR #3587's shape).
