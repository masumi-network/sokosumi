# CMO signs in through Core's OAuth provider

CMO lives at app.cmo.xyz, on its own registrable domain (cmo.xyz), so it cannot share Sokosumi's session cookie, which Core only widens to `*.sokosumi.com`. Sign in with Sokosumi therefore runs through the OAuth provider Core already hosts for the CLI and Apple clients: CMO is a confidential client that exchanges the code server side, keeps the tokens in an encrypted cookie on app.cmo.xyz because it has no database, and calls Core `/v1` only from its server with the `sokosumi:api` token and the `x-organization-slug` header. Core's CORS and trusted origins stay limited to Sokosumi hosts.

## Considered Options

- **Serve CMO from a Sokosumi subdomain and share the cookie.** No auth work, but the product would not live on cmo.xyz.
- **A CMO login form backed by Core's email sign-in.** Production Core sets cookies for `sokosumi.com`, which browsers drop on cmo.xyz, so it needed a bearer plugin or per-origin cookie domains. It also lost passkeys, whose relying party is sokosumi.com, and added a second credential surface to protect. It cost more than the OAuth provider that already existed.
- **Previews through production CMO's `oAuthProxy`.** Core only ever saw production CMO's callback; production exchanged the code with mainnet Core and handed the tokens to the preview. No database was written, but a preview ran against mainnet Core, so it could not reach a PR's routes or migrations or test Core auth changes, it carried real mainnet tokens, and it needed production CMO to run the proxy. Used from SOK-1225 until previews moved to the PR's Core preview.
- **Write each preview's callback into the PR's preview database.** CI after `/deploy`, or a Core build step, would add the callback to CMO's client row in the PR's Neon branch. Rejected: it rewrites that database on every deploy and reset, and a preview reset loses it.

## Consequences

- OAuth redirect URIs must match exactly. CMO has one hand-registered client per environment, like the CLI, and production Core never accepts wildcard redirects.
- A PR's CMO preview signs in against the same PR's `sokosumi-core-mainnet` preview, which Vercel names through CMO's related project (a long branch's alias is truncated with a hash, so CMO cannot derive it). Vercel appends CMO's preview suffix (`preview.cmo.xyz`) to that alias, so CMO swaps in Core's (`preview.sokosumi.com`). A preview without one fails instead of falling back to mainnet. The preview's Neon branch forks mainnet, so it already holds production CMO's client and secret. Only a preview Core (`VERCEL_ENV=preview`) also accepts a CMO preview's own callback, `https://sokosumi-cmo-git-*.preview.cmo.xyz/api/auth/callback/sokosumi`, and only for the client registered with production CMO's callback (`https://app.cmo.xyz/api/auth/callback/sokosumi`). The forked database also holds mainnet's ID token signing keys, encrypted with production's `BETTER_AUTH_SECRET`; outside production, Core skips keys it cannot decrypt and Better Auth creates one of its own, while production still fails on such a key rather than replacing it. Previews therefore test a PR's Core changes through CMO, hold no mainnet tokens, and need no CI writes to their database. CMO is mainnet only, so `/deploy preprod` builds no CMO preview.
- Every user sees the consent screen once, because Core's `/v1` bearer check requires a stored consent that grants `sokosumi:api`. (Amended by [ADR 0046](0046-first-party-clients-skip-consent.md): CMO is a first-party client and skips the consent screen.)
- Sign-in, sign-up, and consent pages carry Sokosumi's branding. Signing out of CMO does not sign out of Sokosumi.
- A password sign-up from CMO still gets Core's verification email, but it names CMO, and its link lands on Web's `/auth/email-confirmed`, which says the address is confirmed and links back to CMO's `client_uri` (https only) instead of opening Sokosumi. Verifying still signs the person in to Sokosumi, as every verification does: that session lets the page name CMO, and makes "Return to CMO" sign in on a second device without a password.
- Because Sokosumi's session outlives CMO's, a person already signed in to Sokosumi is never signed in to CMO without a choice they can undo. CMO's "Create account" (`prompt=create`) asks "Continue as" that account or "Use another account", which signs out of Sokosumi and shows the form again with the same signed request. A session that started for the request itself, within five seconds of Core signing it (`ba_iat`), goes back without the question: Core sends a fresh sign-up back to the sign-up page. Sign in sends no prompt and stays automatic, even after a CMO sign-out: a person switches accounts through "Create account" and "Use another account".
- CMO runs Better Auth statelessly with the generic OAuth plugin; its callback is `/api/auth/callback/sokosumi`. Stateless mode stores and renews Core's rotating refresh token in the encrypted account cookie, so no separate OIDC client library is needed.
- Core grants no `profile` or `email` scope, so its ID token and userinfo carry only `sub`. CMO reads the name and email from `GET /v1/users/me` at sign in, naming the session after the first and last name, or the display name when those are not given. It checks that endpoint again after each token refresh, because Core's refresh grant does not reject banned users, so a ban reaches CMO within one access-token lifetime (2 hours) without a Core call on every page. The same call renews the session's name, so a changed first or last name (or display name, for an account without them) reaches CMO within 2 hours too. A 401 or 403 from that check clears CMO's cookies and revokes its current refresh token; when only that check fails for another reason, CMO returns 503 and preserves the session and any rotated cookies. A failed refresh grant signs the person out, whatever the cause, so a Core outage during a refresh (token endpoint or discovery down) ends the session too. When CMO signs a person out this way, it adds `?error=signed_out` to the page they asked for; the home page then says they were signed out, while `/signin` and `/signup` ignore it and start sign in.
- CMO shares renewals by its session and account cookies, including chunked account cookies, and replays cookie-setting responses for 30 seconds so delayed requests do not reuse a rotated token within one process. Across server instances, Core replays the rotation response for 30 seconds (`refreshTokenReuseInterval`) instead of revoking the token family, so CMO keeps no database or shared store. Reuse after 30 seconds still revokes the family. If a refresh overlaps an in-progress rotation, Core retries the validated token endpoint until the stored replay is available, with a total retry delay budget of five seconds. It retries only while the token's row shows a rotation inside the replay window, so expired or mismatched tokens fail at once. Each incoming request still counts once against the HTTP rate limit. If recovery fails, CMO signs out. Single-use DPoP proofs and client assertions are not retried.
